# 目标

把当前正式版本固化为可追溯的版本包 **v0.3.0**：版本号统一、变更记录入库、生产二进制归档为版本化产物并附校验和，最终以 git tag 钉住发布提交并推送远端——后续 main 上的开发与部署不再影响当前正式版本，回滚与审计有据可查。

# 范围

- `package.json` 版本 `0.1.0 → 0.3.0`（与 server.js 的 MCP Server 元数据 0.3.0 对齐；0.2.x 为鉴权加固、0.3.0 为流式上传）。
- 新增 `CHANGELOG.md`：v0.3.0 完整变更记录（新增/修复/部署说明），后续版本在此累积。
- 服务器（10.0.0.11）归档版本化产物：`/opt/ssh-mcp/releases/ssh-mcp-server-linux-v0.3.0`（复制当前生产运行中的 SEA 二进制）+ `SHA256SUMS`。
- git tag `v0.3.0`（注解含源码提交、产物 SHA256、构建环境），归档合并后打在 main 上并随 main 推送远端。

# 非目标

- 二进制不入 git（122MB 产物以 tag + 校验和 + 服务器 releases 目录固化；源码可从 tag 重建）。
- 不改任何功能代码（纯版本元数据 + CHANGELOG）。
- 不引入 CI/CD 自动发版（后续规划）。
- 不改动生产运行方式（现网二进制原地不动，releases 目录只是归档副本）。

# 验收示例

- A1：`package.json` 的 version 为 `0.3.0`，与 `server.js` MCP Server 元数据一致。
- A2：`CHANGELOG.md` 存在且含 v0.3.0 小节，覆盖鉴权加固与流式上传两个特性、修复清单与部署/回滚说明。
- A3：服务器 `/opt/ssh-mcp/releases/` 下存在 `ssh-mcp-server-linux-v0.3.0` 与 `SHA256SUMS`，产物 SHA256 与当前生产运行二进制一致。

# 约束与不变量

- 生产服务不重启、不中断（本 change 不触碰运行中的二进制与服务）。
- tag 必须指向含 A1/A2 产物的发布提交；tag 注解记录产物 SHA256 与构建环境（Node 22 / WSL / SEA）。
- 版本号语义：major.minor 与 MCP Server 元数据保持同步。

# 决策

- D1（用户 2026-09-21"打出一个版本包提交到 git，后续更新不影响正式版"）：采用 git tag + 版本化产物 + 校验和方案固化 v0.3.0；二进制不入库（122MB 不适合进 git，且 SEA 可从 tag 源码重建）。
- D2：版本号定为 0.3.0——对齐 server.js 既有元数据；0.2.x 留给鉴权加固、0.3.0 对应流式上传。
